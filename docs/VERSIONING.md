# 版本、分支与标签管理规范

本规范适用于 `qingStorClient` 仓库的全部内容，包括客户端（`electron/`、`renderer/`）与内置更新服务（`server/`）。
目标只有一句话：**任何时刻，`package.json` 的 `version`、git 标签、安装包文件名、更新服务里的记录四者能互相推导出来，不靠记忆。**

判断自己该做什么时，先看第 0 章的流程，再看第 9 章的硬约束（那一章是可执行规则，不是建议）。

---

## 0. 完整生命周期

> **当前处于「初始开发版」阶段，本章流程暂未启用。** `0.0.1-dev` 直接在 `main` 上、本机手动构建，没有版本分支、没有标签，规则见 [1.3.1](#131-初始开发版当前-001-dev-的特殊约定)。等第一个真正的版本计划启动时，才从下面的 ① 开始。

```
① 开启新版本计划
   定 x 和 y（z 恒为 0）→ 从 main 拉 ver/x.y → 版本号改 x.y.0-dev
        │
        ▼
② 开发
   在 ver/x.y 上迭代 → 推送触发开发包构建（无 tag，不发布）→ 分发试装
        │  同版本可反复重发，需要区分轮次加 -dev.N
        ▼
③ 评估可发布
   功能冻结，验证通过
        │
        ▼
④ 发布 x.y.0
   版本号去 -dev → 推送 → 打 tag vx.y.0 推送 → 合并 main 并推送
        │  CI：校验 tag==version → 三平台构建 → GitHub Release → 上传 stable 渠道
        ▼
⑤ 缺陷修复（z 补丁，分支名不变）
   在 ver/x.y 上修 → z+1，必要时加 -dev 先发开发版验证 → 定版 x.y.z
        │
        ▼
⑥ 发布 x.y.z
   打 tag vx.y.z → 合并 main
        │
        └──▶ 回到 ⑤ 循环，直到决定开启下一个版本（回 ①，新开 ver/x.y+1）
              ↑ 一旦开了 ver/x.y+1，ver/x.y 即永久停止维护
```

四条不变量：

1. **`main` 永远是「最新正式版」的内容**。当前版本线每发布一次，就同步合并一次。
2. **分支名只体现 x.y**，`z` 由分支内的实际版本号决定，不在分支名上体现；标签才是 `x.y.z` 的精确版本。
3. **只有打标签才算正式发布**，其余一切构建都是开发包。
4. **同一时刻只维护一条版本线**，即当前最新的 `x.y`。版本号一旦从 `1.2` 迭代到 `1.4`，`1.2` 即刻终止维护：不再出补丁、不再打标签、不再为它做任何构建。缺陷修复一律落在当前最新版本线上。

## 1. 版本号规范

### 1.1 格式

```
MAJOR.MINOR.PATCH[-prerelease]
   x  .  y  .  z
```

- 唯一来源：**根目录 `package.json` 的 `version`**。Electron 通过 `app.getVersion()` 读取，打包产物文件名由 `${version}` 填充，客户端检查更新时上报的 `current` 也是它。
- 同步项：`package-lock.json` 顶层的 `version` 与 `packages[""].version` 两处（`npm version` 或 `npm install` 会自动同步；手改 `package.json` 时必须一起改，否则 `npm ci` 会报不一致）。lock 文件里其它 `"version": "x.y.z"` 是第三方依赖自身的版本，不要动。
- **不要使用 `+build` 构建元数据**。客户端与服务端的 `parseVersion()` 正则都不认 `+`，`1.2.0+build5` 会被判定为非法版本，服务端上传接口直接拒绝。

### 1.2 x / y / z 各自管什么

| 位 | 含义 | 何时变动 | 判定标准（满足任一条即是） | 本项目典型场景 |
| --- | --- | --- | --- | --- |
| **x**（MAJOR） | 破坏性变更 | 开启新版本计划时定 | 老版本用户升级后会「丢数据 / 打不开配置 / 用不了已有功能」，且没有自动迁移 | 配置文件结构变更且不做迁移；用户数据目录（`userData/`）布局调整；更新服务接口协议不兼容；放弃某个平台或架构；提高最低系统版本（macOS 11 → 12） |
| **y**（MINOR） | 功能更新 | 开启新版本计划时定 | 新增能力，或对已有能力做用户可感知的改动，且向后兼容 | 新增「检查更新」/ 渠道切换；新增批量重命名、目录上传；传输队列支持并发配置；界面整体改版 |
| **z**（PATCH） | 缺陷修复 | **只在修缺陷时 +1** | 行为应当不变，只修不正确的地方 | 修上传中断、修 sha256 校验误判、修路径转义丢字符；依赖升级、日志优化、文案修正、性能优化 |

**关键分工**：`x` 与 `y` 在开启版本计划时一次性定死，之后整条版本线不再变；`z` 是分支内的「计数器」，从 0 起步，只有修缺陷才 +1。

所以看到 `1.2.x` 就能确定：这是同一条版本线，功能集合由 `1.2.0` 定下，后续 `1.2.1`、`1.2.2` 只把它修稳、不会偷偷多出功能。想加功能必须开 `1.3.0`，版本线随之切换。

判断不清时看**老用户会不会受影响**：会受影响就是 x，不会就是 y；只是让原本该work的东西work了，就是 z。

### 1.3 0.y.z 阶段特例（当前所处阶段）

SemVer 原文规定 `0.y.z` 为初始开发阶段，「任何东西都可能随时改变」。本项目当前固定为 **`0.0.x-dev`**，规则放宽如下：

| 项 | 规定 |
| --- | --- |
| 版本号 | `0.0.z-dev`，当前 `0.0.1-dev`。**此阶段 z 当作「开发迭代号」使用**，不受 1.2 节「z 只在修缺陷时 +1」的约束 |
| 分支 | **没有版本线**：初始开发版直接落在 `main` 上，通过本机手动构建分发。不推 `ver/*`，不走 CI 自动构建（见 1.3.1） |
| 破坏性变更 | **只升 z**，不升 x。开发期允许不兼容改动，不入 MAJOR |
| 打标签 | **不打任何标签** |
| 正式发布 | 无计划。开发包在本机打包后直接分发，或上传更新服务 `dev` 渠道 |
| 结束条件 | 出现「要给非开发人员长期使用」的需求时，一次性定版 `1.0.0`，此后严格按 1.2 节执行 |

> 为什么这样定：`0.0.x` 已经是「最低号」，此时再用 MAJOR 表达破坏性变更毫无信息量，反而让 `1.0.0` 这个真正的起点失去意义。开发期的破坏性变更由「用户都是内部测试、随时可覆盖安装」来兜底。

#### 1.3.1 初始开发版（当前 `0.0.1-dev`）的特殊约定

`0.0.1-dev` 是迁移到 Electron 后的**第一个可分发版本**，它本身不是一个「版本线」，按下面四条处理：

1. **直接在 `main` 上，不建 `ver/*` 分支**。它没有可以「从 main 拉出」的前序发布，也没有后续 z 补丁序列，单独造一条版本线只会多出一个空壳分支。
2. **不推版本分支、不打标签**，因此不触发 CI 的三平台构建与 Release。产物由**本机手动构建**：

   ```bash
   npm run dist:win      # Windows（NSIS 安装版 + 便携版）
   npm run dist:mac      # macOS
   npm run dist:linux    # Linux
   ```

3. **`main` 的内容就是当前最新代码**，不涉及「发版后同步 main」这一步——本阶段 `main` 与工作分支合一。
4. **第一个真正的版本计划开始时才建立版本线**：确定目标 `x.y` 后，从 `main` 拉 `ver/x.y`、版本号改为 `x.y.0-dev`，之后按第 5 章正常走。届时 `0.0.1-dev` 的历史留在 `main` 的提交历史里，不追溯补分支、不补标签。

### 1.4 预发布后缀

| 后缀 | 用途 | 示例 | 客户端能否收到 |
| --- | --- | --- | --- |
| `-dev` / `-dev.N` | 开发期构建，对应 `dev` 渠道 | `1.2.0-dev`、`1.2.0-dev.7` | 仅「开发版」渠道 |
| `-alpha.N` | 内部早期预览（如 1.0 大改前） | `1.0.0-alpha.2` | 仅 `dev` 渠道 |
| `-beta.N` | 外部测试版 | `1.1.0-beta.1` | 仅 `dev` 渠道 |
| `-rc.N` | 发布候选，功能冻结只修 bug | `1.1.0-rc.1` | 仅 `dev` 渠道 |

排序语义（客户端与服务端实现一致，按 SemVer 2.0 第 11 条实现）：

```
1.1.0-rc.1    <  1.1.0           ← 正式版发出去后，rc 用户能收到升级
1.1.0-beta.1  >  1.0.0           ← 预发布版能顶掉低号正式版
1.0.0-dev.9   <  1.0.0-dev.10    ← 数字段按数值比，序号过 9 不会错序
1.0.0-dev     <  1.0.0-dev.1     ← 前缀全等时段数少的更小
1.0.0-1       <  1.0.0-alpha     ← 数字段优先级低于字母段
```

`comparePrerelease()` 的规则：

- 按 `.` 切段，**数字段按数值比较**（`dev.9 < dev.10 < dev.99`），字母段按 ASCII 比较（`alpha < beta < rc`）
- 数字段优先级低于字母段
- 前缀全等时段数少的更小

因此在同一目标版本内，`-dev` 后缀随便加序号，**没有上限**，不会出现「迭代到第 10 个构建客户端就收不到更新」的问题。

> 历史说明：旧实现用字符串比较预发布部分，`'dev.10' < 'dev.9'` 成立，序号过两位数就会错序。该缺陷已在 `electron/update.js` 与 `server/server.js` 两端修复。**已安装的旧客户端仍带旧逻辑**，需升级到包含该修复的版本后才生效。

后缀只能用字母、数字、点（正则 `[0-9A-Za-z.]`），下划线、加号、中文会被判为非法版本。

### 1.5 改版本号的操作规程

- **单独一个提交**，不与功能代码混在一起：`chore(release): 1.2.0`。
- 改完立刻核对两处一致：

```bash
node -p "require('./package.json').version"
grep -m2 '"version"' package-lock.json     # 应为同一个值
```

- 客户端与服务端是**两套独立版本号**，各改各的：`package.json`（客户端）与 `server/package.json`（服务端），互不牵连。

## 2. 分支规范

### 2.1 分支模型

```
main                     ●────────●────────────●──────────●   ← 永远是最新正式版的内容，标签打在这里
                          \       /            /          /
ver/1.2                    ●──●──●────────────●──────●───●     ← 版本线：1.2.0-dev → 1.2.0 → 1.2.1…
                            \  /                （z 补丁仍在同一条分支，分支名不变）
feat/xxx  fix/yyy            ●●                               ← 短期工作分支，合并即删
```

上图的 `ver/1.2` 只在 `ver/1.3` 开启之前向右延伸。**`ver/1.3` 一旦建立，`ver/1.2` 的右端就此封口**——它不会被删除、历史也完整保留，但不再接收任何提交与标签。

### 2.2 各分支职责

| 分支 | 长期/短期 | 能否直接提交 | 推送到远端会发生什么 | 说明 |
| --- | --- | --- | --- | --- |
| `main` | 长期 | 仅合入发版提交 | **不触发构建** | 永远保持「最新正式版」内容，标签打在这里 |
| `ver/<x.y>` | 长期（一个版本一条，**仅最新一条活跃**） | 仅当前最新一条可以 | **触发三平台开发包构建**（artifacts，14 天） | 版本线。**当前尚未建立任何版本线**（初始开发版 `0.0.1-dev` 直接在 `main` 上，见 1.3.1）。被下一条取代后转为只读，不再提交 |
| `feat/<描述>` | 短期 | 可以 | 不触发构建 | 跨多天、影响面大的功能，完成后合并进当前 `ver/x.y` |
| `fix/<描述>` | 短期 | 可以 | 不触发构建 | 非紧急缺陷修复，合并进当前 `ver/x.y` |
| `chore/`、`docs/`、`refactor/` | 短期 | 可以 | 不触发构建 | 构建脚本、文档、无行为变更的重构 |

命名只用小写字母、数字、连字符与 `/`。`ver/` 前缀**不要乱起**——CI 以 `ver/**` 作为「这是开发构建」的判据，误建 `ver/` 开头的临时分支会白跑一次三平台构建。

**没有 `hotfix/` 分支。** 本项目只维护当前最新版本线，旧版本线终止维护后不再接收任何修复，因此不存在「从旧标签拉 hotfix 出补丁」这条路径（原因见 5.5）。缺陷一律在当前 `ver/x.y` 上按 `z+1` 处理。

### 2.3 分支名与版本号的对应关系

| 分支名 | 承载的版本号 | 说明 |
| --- | --- | --- |
| `ver/1.2` | `1.2.0-dev` → `1.2.0` → `1.2.1-dev` → `1.2.1` → `1.2.2` … | **只体现 x.y**，`z` 在分支内决定、不在分支名上体现 |
| `ver/1.3` | `1.3.0-dev` → `1.3.0` … | 下一个版本线，从 `main` 拉出 |

- 分支名不带 patch：`z` 是分支内的计数器，把 `.0` 写进分支名会让它在发出 `1.2.1` 后立刻过时。
- 精确版本只认**标签**：`v1.2.0`、`v1.2.1` 各自对应一次发布，分支始终叫 `ver/1.2`。
- 一条版本线依次走三个阶段，之后永久进入终止状态：

| 阶段 | 版本号 | 分支上做什么 | 产物去向 |
| --- | --- | --- | --- |
| 开发 | `x.y.0-dev`（可加 `.N`） | 功能开发、反复迭代 | 推送 `ver/x.y` → Actions artifacts + `dev` 渠道 |
| 发布 | `x.y.0` | 去后缀 → 提交推送 → 打标签 `vx.y.0` → 合并 `main` | GitHub Release + `stable` 渠道 |
| 维护 | `x.y.z-dev` → `x.y.z` | **只修缺陷**，不动功能 | 同上，标签 `vx.y.z` |
| 终止维护 | — | **永久不再改动**：不出补丁、不打标签、不为它构建 | — |

四条必须守住的规则：

1. **一条版本线只承载一组功能**。`x.y.0` 定下的功能集合是这条线的全部内容，后续 z 补丁只修不增。要加功能就开新分支 `ver/x.y+1`（从 `main` 拉），否则分支名与实际功能集合脱节。
2. **发版后不要删除版本线**。它记录「这条线从 dev 一路到最后一个补丁」的完整历史，也是回滚与追溯的依据。
3. **新版本线的起点是 `main`**，不是上一条版本线的末端——`main` 里已是上一条线最后一次发布的代码。
4. **只有当前最新版本线处于「维护」阶段，其余全部终止维护**。开启 `ver/1.4` 的那一刻，`ver/1.2` 就从「维护」翻转为「终止维护」——即使它才刚发完 `1.2.5`、即使还有用户在跑 `1.2`。判定一个版本线是否在维护，只看一件事：**它是不是当前最大的 `x.y`**。

**当前状态**：**没有任何活跃版本线。** 初始开发版 `0.0.1-dev` 直接位于 `main`，由本机手动构建，不建 `ver/*`、不打标签（见 1.3.1）。第一个版本计划启动时，才从 `main` 拉出第一条 `ver/x.y`；届时 `main` 已是「最新（开发期）代码」，不需要额外合并。

## 3. 标签规范

### 3.1 两套标签空间

| 对象 | 标签格式 | 示例 | 版本来源 | 触发什么 |
| --- | --- | --- | --- | --- |
| 客户端 | `v<x.y.z>[-pre]` | `v1.2.0`、`v1.3.0-beta.1` | 根 `package.json` | 三平台构建 + GitHub Release |
| 服务端 | `server-v<x.y.z>` | `server-v1.2.0` | `server/package.json` | 无 CI；`docker-publish` 脚本据此校验并打镜像标签 |

**服务端标签必须带 `server-v` 前缀，这是硬要求不是风格偏好。** 两套版本号共用同一个 git 标签空间，而 `docker-publish.sh` / `.ps1` 会用 `git tag --match 'server-v*'` 读 HEAD 上的标签并与 `server/package.json` 做严格相等校验。若用裸 `v1.1.0` 打服务端版本，脚本要么读不到（报找不到标签），要么被客户端的 `v*` 标签干扰后比对失败而拒绝发布。

### 3.2 打标签的规矩

- **标签打在「发布提交」上**，也就是改完版本号、准备发布的那次提交。它必须满足两个条件：
  1. 该提交的 `package.json` 版本与标签名一致（CI 第一步守着）；
  2. 该提交最终进入 `main`（当前版本线发布时必须合并 `main`，见 5.3）。
- **用附注标签**（`git tag -a`）而非轻量标签，让标签携带发布者与说明：

```bash
git tag -a v1.2.0 -m "QingStorClient 1.2.0"
```

- **标签名去掉 `v` 后必须严格等于 `package.json` 的 `version`**。CI 第一步就是这道守卫，不一致直接 `exit 1`：

```
tag=v1.2.0  package.json=1.2.0      → 通过
tag=v1.2.0  package.json=1.2.0-dev  → 失败（这也正是 v0.0.x 阶段不许打标签的技术原因之一）
```

- **已推送的标签不许移动、不许删除后重打**。标签是「这个版本就是这堆代码」的唯一凭证，重打会让已安装用户与仓库状态对不上。发错了就往前发一个 z+1。
- **只给当前最新版本线打标签**。旧版本线一旦终止维护，就不再新增任何 `v*` 标签——`v1.2.3`（给已退役版本补出的包）不应该存在。
- 标签名含 `-` 时 CI 自动标记为 prerelease，不会顶掉 GitHub 的 `latest`。
- **`0.0.x` 开发期一律不打任何标签**（包括 `v0.0.1-dev`）。

## 4. 版本号 → 渠道 → 产物 对照表

| 版本号形态 | 渠道 | 产物来源 | 客户端默认能收到吗 |
| --- | --- | --- | --- |
| `0.0.1-dev`、`1.2.0-beta.1` | `dev` | Actions artifacts，或上传到更新服务的 `dev` 渠道 | 否，需手动把状态栏徽标切到「开发版」 |
| `1.2.0`（无后缀） | `stable` | GitHub Release，或上传到更新服务的 `stable` 渠道 | 是 |

- 渠道隔离由请求参数 `channel` 完成，两条渠道的版本号各自演进、互不可见。
- 客户端**不做降级**：从 `dev` 切回 `stable` 时若 stable 最新版低于当前版本，提示「已是最新」，不会回退安装。
- 服务端对「渠道 + 版本 + 平台 + 架构」采用**覆盖**语义。

### 覆盖重发的适用边界（重要）

| 场景 | 能否覆盖重发同号包 | 原因 |
| --- | --- | --- |
| `dev` 渠道 / `x.y.z-dev` | **可以** | 开发期改完直接重发 `1.2.0-dev` 即可，不必为了重发而升版本号 |
| `stable` 渠道 / 正式版 | **不可以** | `1.2.0` 的用户检查更新时 `current == latest`，判定为「已是最新」，**永远收不到重发的包**。服务端的记录虽被覆盖，但对老用户无效 |

正式版若发现包有问题，唯一正确做法是**升 z 发新版本**（`1.2.1`），不能覆盖重发。这也是「正式版发出去就不可撤销」的由来——发布前必须在版本线上把开发包验证到位。

## 5. 全流程（逐条可执行）

### 5.1 ① 开启新版本计划

**先定 `x` 和 `y`，`z` 恒为 0。** 判断依据见 1.2 与第 6 节：破坏性变更 → x+1（y 归零）；新功能 → y+1。

```bash
# 1. 从 main 拉版本线（main 是最新正式版，起点必须在这里）
git checkout main && git pull
git checkout -b ver/1.3

# 2. 把版本号改成开发版：x.y.0-dev（根 package.json + package-lock.json 两处）
#    "version": "1.3.0-dev"
git add package.json package-lock.json
git commit -m "chore: 开启 1.3.0 开发"

# 3. 推送触发首次开发包构建（无 tag，不会建 Release）
git push -u origin ver/1.3
```

### 5.2 ② 开发与 ③ 分发试装

开发期内**版本号不用动**：同一目标版本反复构建、反复上传，都叫 `1.3.0-dev`，服务端 dev 渠道是同号覆盖。需要区分「第几次构建」时再加序号（`1.3.0-dev.1`、`-dev.2`……，序号无上限，见 1.4）。

大功能走 `feat/xxx` 短分支，完成后合进 `ver/1.3`；`feat/*` 推送不触发构建，不浪费 CI。

分发两条路径：

```bash
# 方式 A：Actions artifacts（开发自测）
#   GitHub → Actions → 对应 commit 的 Build Desktop App → 下载 qingstor-client-win/mac/linux
#   产物保留 14 天

# 方式 B：更新服务 dev 渠道（测试同学用，能验证「检查更新」完整链路）
#   1. SSH 隧道开管理口（公网没有入口）
#   2. 浏览器打开 http://127.0.0.1:8790/admin，粘贴 data/admin-token.txt 里的令牌
#   3. 选安装包 → 版本/平台/架构从文件名自动填充 → 校验后上传
#      ⚠ platform / arch 必须与客户端上报一致（Windows x64 → win + x64），否则查不到
```

上传后，客户端把状态栏徽标切到「开发版」，点版本号即可验证「发现新版 → 下载 → sha256 校验 → 运行安装器」全链路。

**迭代到「评估可以发布正式版」为止**：功能齐全、开发包在目标平台跑通、没有已知阻塞缺陷。这个判断没有客观标准，由发起版本计划的人确认。

### 5.3 ④ 发布 x.y.0

前置条件（缺一不可）：功能已冻结、验证通过；`x.y.0` 按 1.2 节确认位次正确。

```bash
# ── 1. 在版本线上把版本号定为正式版（只去掉 -dev 后缀，不升位）
git checkout ver/1.3 && git pull
#    编辑 package.json 与 package-lock.json：1.3.0-dev → 1.3.0
git add package.json package-lock.json
git commit -m "chore(release): 1.3.0"

# ── 2. 推送版本线（会再跑一次开发构建，产物是 artifacts，无害）
git push origin ver/1.3

# ── 3. 打附注标签并推送（这一步才真正触发发布）
git tag -a v1.3.0 -m "QingStorClient 1.3.0"
git push origin v1.3.0

# ── 4. 合并进 main：让 main 永远等于最新正式版
git checkout main && git pull
git merge --no-ff ver/1.3 -m "chore(release): 合并 ver/1.3 发布 1.3.0"
git push origin main

# ── 5. 校验：tag 指向的提交必须已在 main 上
git merge-base --is-ancestor v1.3.0 main && echo "OK: tag 已进入 main"
git show v1.3.0:package.json | grep '"version"'     # 应为 "1.3.0"

# ── 6. 等 CI：校验 tag==version → 三平台构建 → 自动建 GitHub Release
#     任一平台失败则整体不发版；修完发 1.3.1，不要重打 v1.3.0

# ── 7. 从 Release 下载安装包 → 上传更新服务 stable 渠道
#     平台/架构务必匹配：win/x64、mac/arm64、mac/x64、linux/x64 …
```

第 3、4 步的次序可以互换（先合并再打标签也行），但结果必须同时满足：**tag 指向的提交在 `main` 上**、`main` 的 `version` 等于该 tag。第 5 步就是校验这件事。

**不要**在发版后往这条版本线上加功能——那是 `1.4` 的事，会破坏「一条版本线一组功能」的对应关系。

### 5.4 ⑤ 缺陷修复 → ⑥ 发布 x.y.z

`z` 只在修缺陷时 +1，**分支名不变，仍是 `ver/x.y`**。

```bash
# ── 1. 在版本线上修（功能不动）
git checkout ver/1.3 && git pull
git commit -am "fix: 修复 XXX 崩溃"

# ── 2. 更新 z，并按需加 -dev 先走开发版验证
#    "version": "1.3.1-dev"
git commit -am "chore: 开启 1.3.1 补丁"
git push origin ver/1.3                    # → 开发包

# ── 3. （可选）开发版分发验证：上传 dev 渠道 / 取 artifacts 试装
#      改动小、可确定时可以直接跳到第 4 步

# ── 4. 定版并发布 x.y.z
#    "version": "1.3.1"
git commit -am "chore(release): 1.3.1"
git push origin ver/1.3
git tag -a v1.3.1 -m "QingStorClient 1.3.1"
git push origin v1.3.1
git checkout main && git merge --no-ff ver/1.3
git push origin main
git merge-base --is-ancestor v1.3.1 main && echo "OK"
```

发布后回到第 1 步，继续下一轮补丁（`1.3.2`……），**前提是 `ver/1.3` 仍是当前最新版本线**。一旦开启 `ver/1.4`，这条线立即终止维护，不再接收任何补丁（见 5.5）。**补丁必升 z，不允许覆盖重发同号正式版**（原因见第 4 节）。

### 5.5 旧版本线已终止维护（不出补丁）

**原则：只维护当前最新版本线 `x.y`。版本号一旦从 `1.2` 迭代到 `1.4`，就代表 `1.2` 已经终止维护，不再有任何补丁。**

场景：`main` 已是 `1.4.0`，用户反馈的问题出现在 `1.2.0` 上。

```bash
# ── 1. 先确认：问题在当前最新版本上还在不在？
git checkout ver/1.4 && git pull
#    在 1.4 上复现/检查该缺陷

# ── 2. 两种情况，处理方式不同
#    a) 新版本已不存在该问题 → 无需任何操作，引导用户升级
#    b) 新版本仍存在该问题 → 就在 ver/1.4 上修，按 5.4 走 z 补丁（1.4.1）
git commit -am "fix: 修复 XXX（1.2 时代遗留）"
#    "version": "1.4.1" → 打 tag v1.4.1 → 合并 main
```

**禁止事项（硬性）**：

- 禁止从旧标签（`v1.2.2`）拉任何分支去出 `1.2.3`。
- 禁止给已终止维护的版本线打新标签，`v1.2.3` 这个标签永远不应该存在。
- 禁止为旧版本线重新构建、重新上传渠道。
- 旧版本线已有的历史标签**保持不动**（它们是发布事实），只是不再新增。

**为什么不给旧线出补丁**：

| 原因 | 说明 |
| --- | --- |
| 语义唯一性 | 「当前版本」必须有唯一答案。`1.4.0` 已发布却还在发 `1.2.6`，等于同时存在两个「最新版」，渠道与文档都无法自洽 |
| 维护成本 | 同一修复要在 N 条线上分别验证、构建、上传，本项目没有多线并行的验证人力，容易出「某条线漏传包」的静默故障 |
| 分叉风险 | 旧线与主线早已分叉，回移植极易漏改；且旧线标签不在 `main` 上，与「标签所指提交必须进入 `main`」的规则直接冲突 |
| 更新链路 | `stable` 渠道的「最新版」是单一值，老线补丁发出去也只能覆盖同号包，对已装 `1.2.0` 的用户反而会因 `current == latest` 收不到（见第 4 节） |

**如果老用户短期升不上去**（例如 `1.4` 有破坏性变更、迁移成本高）：这不是恢复多线维护的理由，而是说明 `1.4` 的升级路径没做好。正确做法是补兼容或补迁移工具，让用户能升上来——也正因如此，`x` 位变更必须在开启版本计划时就慎重评估。

### 5.6 服务端（更新服务）发版

服务端与客户端版本号完全独立，走自己的标签与发布脚本。

```bash
# 1. 改 server/package.json 的 version（如 1.1.0 → 1.2.0）
git commit -am "chore(server): release 1.2.0"

# 2. 打服务端标签（必须在 HEAD 上，脚本会读它做校验）
git tag -a server-v1.2.0 -m "qingstorclient-server 1.2.0"
git push origin server-v1.2.0

# 3. 构建并推送镜像（会自动核对标签与 package.json 是否一致）
cd server
./docker-publish.sh --dry-run     # 先确认 tag 与仓库地址
./docker-publish.sh               # 真推，默认同时推 Docker Hub 与阿里云 ACR
```

- 正式号自动附带 `:latest`；带 `-` 的预发布号不会动 `latest`。
- 服务端只做「分发安装包 + 版本查询」，**升级服务端不影响已安装的客户端**；但改动 `/api/releases/latest` 的响应结构属于破坏性变更，需客户端同步兼容后再发。

## 6. 速查决策表：这次改动该升哪一位

| 改动内容 | 版本位 | 举例 |
| --- | --- | --- |
| 配置文件字段重命名、且不做迁移 | x | `config.json` 的 `endpoint` 拆成 `endpoint` + `region` |
| 更新服务接口不兼容变更 | x | `/api/releases/latest` 响应结构改嵌套 |
| 放弃某平台/架构 | x | 不再构建 `linux/armv7l` |
| 提高最低系统版本 | x | macOS 11 → 12 |
| 新增功能 | y | 新增「同步目录」、新增渠道、新增语言 |
| 已有功能的可感知改动 | y | 传输面板改版、菜单结构调整 |
| 新增可选配置项（有默认值、旧配置照常读） | y | 新增「并发数」设置 |
| 修崩溃 / 修逻辑错误 / 修文案 | z | 修复中断后残留 `.part` |
| 依赖升级、无行为变更的重构、注释与文档 | z | 升级 electron |
| 只改 README、CI 脚本 | 不升版本 | 不影响产物内容 |
| 缺陷只出现在已终止维护的旧版本线 | **不回旧线修**，在当前线按 z 处理 | `1.2` 用户报的问题，在 `1.4` 上确认后修成 `1.4.1` |

**边界情况的判法**：先问「用户升级后原有数据和习惯会不会被打断」。会 → x；不会但多了东西 → y；纯粹变正确了 → z。

再补一条时间维度的判法：**这个功能发布过了吗？** 已发布 → 只能走 z 补丁（只修不增）；未发布（还在 `x.y.0-dev` 阶段）→ 随便改，版本号不用动。

再补一条版本维度的判法：**这个缺陷该修在哪条线上？** 永远只修当前最新版本线。已经迭代掉的旧版本线不接修复，老用户唯一的路径是升级。判断「当前线」只看 `main` 的 `version` 前两位，不看你手上这条分支叫什么。

## 7. 已知陷阱与禁止事项

| 陷阱 | 后果 | 正确做法 |
| --- | --- | --- |
| 标签名与 `package.json` 不一致 | CI 在第一步 `exit 1`，发布中断 | 先定版本号并提交，再打标签 |
| 用裸 `v1.1.0` 打服务端版本 | `docker-publish` 校验失败，镜像发不出去 | 服务端一律 `server-v*` |
| 给已终止维护的旧版本线出补丁（从旧标签拉 `hotfix/`、打 `v1.2.3`） | 同时存在多个「最新版」，渠道与文档无法自洽；旧线标签还不在 `main` 上 | 只在当前最新版本线按 z 修，老用户升级上来 |
| 发布后忘记合并 `main` | `main` 落后，下次开新版本线会从旧代码起 | 每次发版都执行 5.3 第 4、5 步 |
| 覆盖重发同号正式版 | 老用户永远收不到（`current == latest`） | 升 z 发新版本 |
| 在已发布的版本线上加新功能 | 分支名与实际功能集合脱节，`1.3.x` 里混进 1.4 的功能 | 新功能开 `ver/x.y+1` |
| 分支名写成 `ver/1.2.0` | 发出 `1.2.1` 后名字立刻过时 | 分支只带 `x.y` |
| 使用 `+build` 元数据 | 客户端与服务端 `parseVersion` 都判非法 | 不用构建元数据 |
| 只改 `package.json` 不改 `package-lock.json` | `npm ci` 报版本不一致，CI 失败 | 两处同改，或用 `npm version` |
| 在 `0.0.x` 阶段打标签 | 触发 Release，与「无正式发布计划」冲突 | 开发期只用 artifacts 与 `dev` 渠道 |
| 上传安装包时 platform/arch 填错 | 客户端查不到更新，且不报错 | Windows x64 → `win` + `x64`，与客户端上报对齐 |
| 建 `ver/` 开头的临时分支 | 白跑一次三平台构建（CI 以 `ver/**` 判据） | 临时分支用 `feat/`、`fix/`、`chore/` |

## 9. 执行约束（AI 与人共用）

这一章是**硬性规则**，不是风格建议。任何一条不满足，都视为违规操作，必须停下来修正后再继续。

### 9.1 十条硬约束

| # | 约束 | 违规后果 |
| --- | --- | --- |
| 1 | 版本号只在三个时刻改：开启新版本（`x.y.0-dev`）、定版发布（去掉 `-dev`）、发补丁（`z+1`）。其余时间不动 | 版本线混乱，产物无法区分 |
| 2 | 改 `version` 必须同改 `package-lock.json` 的两处 | `npm ci` 失败，CI 红 |
| 3 | 分支名必须是 `ver/<x.y>`，且 `x.y` 与当前 `version` 的前两位一致（**唯一例外**：初始开发版 `0.0.1-dev` 在 `main` 上，无版本分支，见 1.3.1） | 分支与版本脱节 |
| 4 | 长期分支只有 `main` 和 `ver/*`；临时分支用 `feat/`、`fix/`、`chore/`、`docs/`、`refactor/`（**不设 `hotfix/`**） | 误触发三平台构建；多出一条旧线维护路径 |
| 5 | 打标签前 `version` 必须无 `-dev` / `-beta` 等后缀（预发布标签除外） | `0.0.1-dev` 打标签 = 违反开发期约定 |
| 6 | 标签名 = `v` + `version`，字符级严格相等 | CI 守卫直接失败 |
| 7 | 当前版本线每次发布后必须合并 `main` | `main` 落后，下次开发起点错 |
| 8 | **只维护当前最新版本线**。版本号进入下一条 `x.y` 后，旧线立即终止维护：不出补丁、不打标签、不为它构建；缺陷只在当前线按 `z+1` 修 | 同时存在多个「最新版」，更新渠道与文档全部失效 |
| 9 | 已推送的标签禁止移动、删除、重打 | 用户与仓库状态对不上 |
| 10 | 正式版禁止覆盖重发同号包 | 老用户永远收不到更新 |

### 9.2 操作后自检（每次动版本号或打标签后跑）

```bash
# 1. 版本号与 lock 是否一致
node -p "require('./package.json').version"
grep -m2 '"version"' package-lock.json

# 2. 分支名是否与版本前两位匹配
git branch --show-current          # 应为 ver/x.y，且与上一行版本号前两位一致
#    初始开发版（0.0.x-dev）例外：应在 main 上，没有 ver 分支

# 3. 工作区是否干净（打标签前必须干净）
git status --porcelain

# 4. 标签应该是什么（拿去和实际 tag 比对）
node -p "'v' + require('./package.json').version"

# 5. 标签是否已进入 main（当前版本线发布时必须通过）
git merge-base --is-ancestor v1.2.0 main && echo "OK"

# 6. main 的版本是否等于该标签
git show main:package.json | grep '"version"'

# 7. 手上这条是不是当前唯一在维护的版本线（只应有一条 ver/*）
git branch -r | grep 'origin/ver/'
#    若远端存在 x.y 更高的 ver 分支，说明你手上这条已终止维护，不要在里面提交修复
```

### 9.3 不确定时的处理原则

- **分不清该升哪一位** → 按 `z` 处理（最保守），并在提交信息里说明理由。
- **不确定是否该发布** → 不发布，继续在开发版迭代，等明确的「可以发」信号。
- **线上正式版出了问题** → 升 `z` 发新版本，绝不覆盖重发。
- **想改已发布版本的功能** → 不能改，开下一个 `y`。
- **缺陷报在旧版本上** → 不回旧线修。先在当前最新版本线确认是否仍存在，存在就按 `z` 修在当前线，不存在就引导升级。
- 以上几条仍无法判断时，**停下来问**，不要自行决定版本号。

## 附：一句话记忆

> **x 断代、y 增量、z 修补；开版本从 main 拉 `ver/x.y`、版本号写 `x.y.0-dev`；`ver/*` 出开发包不发布，`v*` 才出正式包；发一次就把 `main` 同步一次；分支只带 `x.y`，标签才是 `x.y.z`；只维护当前最新那条线，旧线一迭代即终止维护、永不再出补丁。**
